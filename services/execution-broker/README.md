# Execution broker implementation status

`outputs.mjs` implements bounded snapshots of job output text files. It checks absolute roots and linked ancestors; rejects symbolic links, junctions, hard-linked files, non-regular files, unsafe portable names and case collisions; limits entries, files, depth and bytes; verifies file identity/size/time around handle reads; validates UTF-8 and JSON; and records hashes. Returned bytes are independent copies, not later reads from job-owned paths.

Supported outputs are text, Markdown, CSV, JSON, HTML and JS/Python source. HTML and source remain inert artifacts. No preview, execution, permission grant, network request or destination write occurs. Media validation is not implemented; unsupported types are rejected rather than labeled safe.

The caller must first terminate the entire job and take exclusive custody of its output directory. These checks are not a race-proof filesystem sandbox against an active process or another process running as the Windows owner. The future broker must establish that custody; a caller-supplied flag is not proof. Hard-link rejection and before/after checks supplement that prerequisite, not replace it.

Five focused synthetic tests passed on Windows on 2026-09-14. Tests cover copied bytes remaining unchanged after source modification, malformed content, unsafe extensions, hard links, junctions/linked ancestors, per-file bytes, nesting depth, entry count and file count. Total-byte policy, case collisions on a case-sensitive filesystem, active-writer races and actual container extraction still require broader qualification.

`artifacts.mjs` adds storage admission under a caller-provided UUID job identifier. It writes a private staging directory, flushes individual files and a receipt, verifies stored bytes, then renames the directory into its published location. Readers only address the published job directory and revalidate file hashes. Existing jobs are never overwritten. Stale locks block admission; failed staging data is preserved for investigation. The trusted store must already exist under owner-only permissions. This library does not provision ACLs or defend against an owner concurrently modifying the store. Filesystem power-loss durability and interrupted-process recovery remain unqualified; file fsync and directory rename alone do not prove those journeys.

Nine combined output/storage tests passed on Windows on 2026-09-14. Added checks cover publication/readback, retained source bytes, overwrite rejection, invalid input leaving prior artifacts unchanged, altered content and permission fields, overlapping paths and stale writer locks. Receipts say `stored-unreviewed` and cannot confer execution permission. Their job IDs still need to be bound to authoritative broker job records; the storage API does not itself prove that a job ran or was authorized.

Not implemented: WSL distribution/container provisioning, job authorization, isolated launch, process-tree cancellation, resource accounting, default-deny network enforcement, media validators, broker-bound receipts, and complete containment tests. Generated-code execution is therefore unavailable, rather than an implemented feature hidden behind a toggle.

`jobs.mjs` adds persistent prepared/running/cancelling/terminal records with revision checks, single-writer locks, atomic file replacement and input hashes. Terminal success requires zero exit and reported process-tree termination from the same container identity; terminal records cannot run again. Startup reads retain running/cancelling state and return `needsRuntimeReconciliation`, with no automatic restart. The caller remains responsible for obtaining trustworthy observations from the actual runtime adapter. These fields are not proof of isolation, consent or runtime termination by themselves.

Twelve combined tests passed after adding lifecycle persistence, mismatched-runtime rejection, missing-termination rejection, stale-revision rejection and restart reconciliation behavior. There is still no runtime adapter, job-launch route or authoritative binding between these job records and artifact receipts. No generated job has been executed by this library.

Subsequently, `admitCompletedJobOutputs` and `readCompletedJobArtifacts` bind receipts to a succeeded job record's ID, revision, input hash and container identity. The completed-job interface rejects non-success jobs and absent or altered bindings. The lower-level `admitOutputs`/`readArtifacts` interface remains storage-only, with no assertion that a job ran; it cannot substitute for completed-job retrieval. Fifteen combined tests passed after this integration. These are synthetic lifecycle observations, not actual container execution. Actual container provenance still depends on the unimplemented trusted runtime adapter and protected job store. Receipts are integrity metadata, not signed attestations against a malicious local owner.
